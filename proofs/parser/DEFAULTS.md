# Defaults settings as data (PLAN stage P5, Rust side)

`Directive::Defaults` carries the settings modifiers of a `Defaults` line. Until this change a
modifier was a `Box<dyn FnOnce(&mut Settings)>` and `SettingKind` held `fn` pointers, so neither
`Directive` nor `Sudo` could be extracted (PLAN 3.1, 6). Both are now plain data generated by the
`defaults!` DSL (`src/defaults/settings_dsl.rs`, table in `src/defaults/mod.rs`); no type or
value in `src/defaults` outside the test oracle `legacy.rs` contains a closure, `dyn` or a `fn`
pointer.

## Data design

```rust
pub enum ListMode { Set, Add, Del }

pub(crate) enum Setting { always_query_group_plugin, ..., env_delete }      // every setting
pub(crate) enum IntegerSetting { umask, passwd_tries, passwd_timeout, timestamp_timeout }
pub(crate) enum TextSetting { lecture, mailerpath, runcwd, apparmor_profile, secure_path,
                              verifypw, timestamp_type, editor }
pub(crate) enum ListSetting { env_keep, env_check, env_delete }

pub(crate) enum SettingsModifier {       // one variant per setting, in table order
    use_pty(bool), umask(u64), lecture(enums::lecture), secure_path(Option<Box<str>>),
    editor(Box<str>), env_keep((ListMode, Vec<String>)), ...
}

#[repr(u32)]                             // hardened discriminants, as before
pub enum SettingKind {
    Flag(SettingsModifier),              // the modifier that sets the flag
    Integer(IntegerSetting),
    Text(TextSetting),
    List(ListSetting),
}
```

Functions (all generated by the DSL except the last three, which are ordinary functions in
`mod.rs`):

| Function | Meaning |
|---|---|
| `SettingsModifier::apply(self, &mut Settings)` | the effect of the old closure: assigns the payload to the field of the variant; for a list, `apply_list(field, mode, items)` |
| `negate(&str) -> Option<SettingsModifier>` | `!name`: the explicit negation `(!= v)` of the table, else `false` for a flag and `(Set, [])` for a list, else `None` |
| `set(&str) -> Option<SettingKind>` | the kind of a setting; a flag carries `x(true)` |
| `check_integer(IntegerSetting, &str) -> Option<SettingsModifier>` | the old `Integer` checker |
| `check_text(TextSetting, &str) -> Option<SettingsModifier>` | the old `Text` checker |
| `build_list(ListSetting, ListMode, Vec<String>) -> SettingsModifier` | the old `List` builder |
| `setting_at(usize) -> Option<(&'static str, Setting)>`, `setting_named(&str) -> Option<Setting>` | the name table and its lookup, used by `negate` and `set` |
| `apply_list`, `integer_in_range`, `octal_mode`, `fractional_minutes` (with `find_dot`, `decimal`) | list effect and value parsers |

Invariants, all by construction of the macro (and checked by the tests below):

1. `IntegerSetting`, `TextSetting`, `ListSetting` and the flags partition the settings; the kind
   of a setting is fixed by the shape of its table entry (`true`/`false`: flag; `[..]` list:
   list; `[a..=b]` or `{fn}`: integer; `[keys]`, `None` or any other expression: text). So
   `check_integer` is total on exactly the settings that `set` reports as `Integer`, and so on:
   the kind cannot disagree with the identity, which the old `fn` pointers did not make visible.
2. The payload type of a variant is the type of its `Settings` field, except for lists, whose
   payload is the change `(ListMode, Vec<String>)`.
3. `apply` writes exactly the field of its variant and nothing else.
4. `negate(n).is_some()` implies `set(n).is_some()`; `negate` is `Some` exactly for flags, lists
   and the settings with an explicit `(!= v)`.
5. `setting_at` enumerates the settings in table order with their names (`stringify!`), each
   once; `setting_named(n)` is the setting whose name equals `n`. The names are the
   field names of `Settings`.
6. `Settings` keeps its fields, accessors, `Default` and `Clone`; `Settings::to_auth` and the
   extracted `defaults.Settings` structure are unchanged (only source-location comments in the
   generated Lean moved). Under `cfg(test)` `Settings`, `SettingsModifier`, `SettingKind`,
   `ListMode` and the setting enums derive `Debug`/`PartialEq`/`Eq`.

## Old to new

| Before (`70fdb56b`) | Now |
|---|---|
| `type SettingsModifier = Box<dyn FnOnce(&mut Settings)>`, applied as `modifier(&mut s)` | `enum SettingsModifier`, applied as `modifier.apply(&mut s)` (`sudoers/mod.rs`, `policy.rs` tests) |
| `move \|obj\| obj.x = v` | `SettingsModifier::x(v)` |
| list closure `match mode { Set => collect, Add => extend, Del => remove each }` | `SettingsModifier::x((mode, items))`; `apply_list`: `Set` = `HashSet::new()` then `insert` each, `Add` = `insert` each, `Del` = `remove` each. `collect` and `extend` build the same set (`collect` is `with_hasher(Default::default())` then `extend`, and `extend` inserts each item) |
| `SettingKind::Flag(closure)` | `SettingKind::Flag(SettingsModifier::x(true))` |
| `SettingKind::Integer(fn(&str) -> Option<SettingsModifier>)` | `SettingKind::Integer(IntegerSetting::x)` + `check_integer` |
| `SettingKind::Text(fn(&str) -> Option<SettingsModifier>)` | `SettingKind::Text(TextSetting::x)` + `check_text` |
| `SettingKind::List(fn(ListMode, Vec<String>) -> SettingsModifier)` | `SettingKind::List(ListSetting::x)` + `build_list` |
| `modifier_of!` | `kind_of!` (the kind), `integer_check!` / `text_check!` (the checker arms), `kind_tables!` (a tt-muncher that sorts the entries into the three setting enums and generates the three functions) |
| `negate`: `"x" if has_standard_negator!(..) => closure(value)`, with a dead `Default::default()` branch for settings without negation | `Some(Setting::x) => Some(SettingsModifier::x(v))` or `None`; `standard_negation!` replaces `has_standard_negator!`, so there is no dead branch |
| `match name { "x" => .. }` in `negate` and `set` | `match setting_named(name) { Some(Setting::x) => .. }` |
| `integer: u64::from_str_radix(..).ok().filter(\|v\| (a..=b).contains(v))` | `integer_in_range(text, radix, a, b)`: the same test written as `a <= v && v <= b` |
| `octal_mode`: `input.strip_prefix('0')?` then `mode_t::from_str_radix(.., 8).ok().map(Into::into)` | first byte `b'0'` checked on `as_bytes()`, then `split_at(1)` (`'0'` is one byte), then `match` |
| `fractional_minutes`: `split_once('.')`, `parse::<u64>()`, `try_into`, `?` | `find_dot` (first `b'.'`; a UTF-8 continuation byte is never `0x2E`), `split_at`, `decimal` (`u64::from_str_radix(_, 10)`, which is what `str::parse::<u64>` calls), `u32::try_from`, `match`; the evaluation order is kept: shift, integral parse, multiplication, fractional parse, addition, `* 60 / shift` |

The parser block `impl Parse for defaults::SettingsModifier` (`src/sudoers/ast.rs`) changed only
at the four call sites of the checkers; its structure, diagnostics and their order are those of
`70fdb56b`.

## Evidence (tests)

`src/defaults/legacy.rs` (`cfg(test)`) keeps the closure DSL of `70fdb56b` verbatim
(`initializer_of`, `modifier_of`, `has_standard_negator`, `ifdef`; `defaults` with the original
matcher and verbatim `negate`/`set`) together with a verbatim copy of the table, of
`octal_mode` and of `fractional_minutes`, applied to the same `Settings`. Its tests compare old
and new by their effect on three base settings: the defaults; every setting moved away from its
default by legacy modifiers (asserted); every negatable setting negated.

| Test | Covers |
|---|---|
| `same_names_and_defaults` | names in table order (legacy table, `Settings` fields, `setting_at`), `Default` |
| `same_kinds` | the kind of every setting and of unknown names |
| `same_negation` | `!name` for every setting and unknown names |
| `same_flags` | the modifier of every flag |
| `same_integers` | the 4 integer settings × 76 inputs: range edges of `passwd_tries`, signs, radix prefixes, octal digits and `mode_t` overflow for `umask`, fractions, empty parts, `u64` overflow and the overflow of `* 60` for the timeouts, non-ASCII bytes next to `0` and `.` |
| `same_texts` | the 8 text settings × 22 inputs: every enum key, case and blank variants, non-keys, paths |
| `same_lists` | the 3 lists × `Set`/`Add`/`Del` × 6 item lists |
| `same_sequences` | every pair of list operations after a negation |
| `same_range_check` | `integer_in_range` against the legacy expression for radix 2, 8, 10, 16, 36 (no table entry has a radix; the radix clause of the old DSL did not compile, since `defaults!` captured it as `expr` and `modifier_of!` matched `literal`) |

`src/sudoers/test/legacy_defaults.rs` copies the old `impl Parse` (with `legacy::` types) and
parses settings texts with both: the 42 `Defaults` lines of the unit tests, 65 further texts that
reach every diagnostic of the settings parser and the checkers at their edges, and lists of 200
variables and 200 settings. Both reject with the same `Status` (span and message) or both accept
and have the same effect on every base. `defaults_directives_old_against_new` parses the full
unit-test lines through `Sudo` and compares the modifiers of the directive with the legacy parse.

A mutation of the range check (`<=` to `<`) fails `same_integers`, `same_range_check` and
`defaults_lines_old_against_new`.

## Extraction

Roots added to `Cargo.toml`: `SettingsModifier::apply`, `set`, `negate`, `check_integer`,
`check_text`, `build_list`. What each needed (ad-hoc `--start-from` runs, then the full run):

| Root | First result | Change |
|---|---|---|
| `SettingsModifier::apply` | extracted; Lean needs `HashSet` `from_iter`, `extend`, `remove`, `RandomState::default`, `Iterator::collect` (missing in the Aeneas library) | `apply_list` with `HashSet::new` and `insert` loops; model of `HashSet::remove` |
| `set`, `negate` | extracted; the generated Lean does not parse: the string `match` becomes 35 nested `if`s and the pretty-printer's indentation collapses near depth 34 (`Str.Insts.CoreCmpPartialEqStr.eq` read as a value, `ite` on a non-`Prop`) | `setting_named` over `setting_at`. A `const` table (slice or array), a `static` table and a local copy of a `const` all fail in Aeneas with `Unimplemented` (promoted constants, references to a `static`, reading the constant); a `match` on the index with one constant per setting extracts |
| `check_integer` | Aeneas fatal: `Unimplemented`, `core::str::pattern` (from `strip_prefix` and `split_once`) | restyled `octal_mode` and `fractional_minutes`; models of `str::as_bytes`, `str::len`, `str::split_at`, `u32`/`u64::from_str_radix`, `u64::pow`, type `ParseIntError` |
| `check_text` | extracted | model of `From<&str> for Box<str>` |
| `build_list` | extracted | none |
| `Settings::default` | the iterator `map` and `collect` have no Aeneas models | reserve capacity and insert the literal keys directly; model `HashSet::with_capacity` as the empty set at the three fixed capacities |

The trusted models are documented in `proofs/lean/ASSUMPTIONS.md`. The reference settings are in
`proofs/spec/SudoersSpec/Settings/`. In `proofs/lean/SudoRsProofs/Defaults/`, the extracted
constructor, producers and `apply` have checked refinement theorems. The constructor's set
fields agree by membership; `apply` agrees even on the list representation. The proof of
`authorization_reachable_eq` uses the producer invariant to discharge `SettingsInRange` for
states reachable from the constructor. It does not establish reachability for scoped Defaults
or connect the settings parser to those producers.

`SYSTEM_EDITOR` is `/usr/bin/editor:/usr/bin/nano:/usr/bin/vi` on Linux, `/usr/bin/vi`
elsewhere. Flags are set to `true` by `name`, whatever their default.

Value parsers, on the text the parser hands over (a `Numeric` token of at most 18 characters
from `0-9a-fA-F.` for integers; a quoted or unquoted string for texts):

- radix 10 / radix 8 (`u64::from_str_radix`, `u32::from_str_radix`): optional single leading
  `+`, then at least one digit of the radix, value within the type.
- `octal_mode(t)`: `t` starts with `0`, the rest is a `u32` in radix 8 (so `0` alone is
  rejected, `00` is 0); the value is widened to `u64`.
- `fractional_minutes(t)`: without `.`: `n * 60` for a radix-10 `n`, rejected on overflow. With
  a first `.` at position `k`: `i = t[..k]`, `f = t[k+1..]`, both radix-10 numbers (both
  non-empty; a further `.` is not a digit), `s = 10^len(f)`, value `(i * s + f) * 60 / s`
  (integer division; an arithmetic overflow panics, which the 18-character token rules out).
- enum: the key exactly as written (case-sensitive).
- text: any string; stored as given (`Some` for the optional ones).
- list: `name = items` replaces the set, `+=` adds, `-=` removes, in item order; `!name` empties it.

Which misuse gives which diagnostic (`impl Parse for defaults::SettingsModifier`, unchanged):

| Input | Diagnostic |
|---|---|
| `!x`, `x` unknown | `unknown setting: 'x'` (from the name) |
| `!x`, `x` has no negation | `'x' cannot be used in a boolean context` (from the name) |
| `x…`, `x` unknown | `unknown setting: 'x'` |
| `x += …` / `x -= …`, `x` not a list | `x is not a list parameter` (once the `=` is read; span from the name) |
| `x = …`, `x` a flag | `can't assign to boolean setting 'x'` |
| `x = v`, `x` integer or text, `v` rejected | `'v' is not a valid value for x` |
| `x`, `x` not a flag | `'x' is not a boolean setting` |
| list values | `double quotes are required for VAR=value pairs`, `empty string not allowed`, `environment variable list too long` |
